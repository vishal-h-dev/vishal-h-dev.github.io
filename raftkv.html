RaftKV — Distributed Key/Value Store on Raft Consensus

A replicated key/value store built on a from-scratch implementation of the Raft consensus algorithm (Ongaro & Ousterhout) — the same protocol behind etcd, Consul, and CockroachDB's metadata layer. Pure Python standard library, zero dependencies.

Python (stdlib) Raft Consensus Leader Election Log Replication TCP Networking Deterministic Simulator 23 Tests

Overview

RaftKV is more than "a dict with an HTTP API." It implements the full Raft protocol — leader election, log replication, and safety under leadership change — as a pure algorithm module with no I/O, wired up to a real TCP transport and CLI for actually running a multi-node cluster.

Consensus Guarantees

Capability How
Leader electionRandomized election timeouts + majority vote — exactly one leader per term, even under message loss.
Log replicationThe leader replicates every command to a majority of nodes, in order, before it's considered committed.
Crash recoverycurrentTerm, votedFor, and the log are fsync'd after every change — a restarted node never forgets a vote or contradicts an accepted entry.
Safety under leadership changeOnly log entries from the current leader's term are committed directly — stale entries from a partitioned-away leader are always safely overwritten.
Partition toleranceA minority partition can never elect a leader or commit anything; once healed, it catches up automatically.

Request Flow

client ──put/get/delete──►any node ──(redirect if not leader)──►leader
                                            │
                                 leader appends to its own log
                                            │
                      AppendEntries RPC ────┼──── AppendEntries RPC
                             ▼                             ▼
                         follower                      follower
                    (persists + acks)             (persists + acks)
                                            │
                      once a majority has persisted it,
                      the leader marks it committed and
                    applies it to its key/value state machine
                                            │
                    followers learn the new commit index on the
                      next heartbeat and apply it too
ModuleResponsibility
core.pyThe pure algorithm — given an RPC, a clock tick, or a client command, decides what to do and returns messages to send. No I/O of any kind.
storage.pyPersists the log and (currentTerm, votedFor) with fsync-on-write, torn-write-detection discipline.
simulator.pyDeterministic, seeded fake network + fake clock used by the entire test suite — no real sockets, no timing-based flakiness.
statemachine.pyThe replicated key/value store + command encoding.
network.py / server.py / client.pyReal TCP transport, per-node service, and client library used by the CLI to run an actual multi-process cluster.

Deterministic Testing

The algorithm itself never touches a socket, thread, or real clock. A seeded, in-process network simulator drives ticks and message delivery explicitly, so consensus edge cases — split votes, partitions, slow followers — are 100% reproducible and never flaky. The same simulator powers the election, replication, and safety test suites end to end.

Running a Real Cluster

A separate real-network layer (TCP transport, per-node service, leader-redirecting client, CLI) lets the same core engine run as an actual multi-process cluster. 

raftkv serve n1 --cluster cluster.json --data-dir ./data
raftkv serve n2 --cluster cluster.json --data-dir ./data
raftkv serve n3 --cluster cluster.json --data-dir ./data

raftkv put --cluster cluster.json foo bar
raftkv get --cluster cluster.json foo          # -> bar
raftkv status --cluster cluster.json           # role/term/commit-index of every node

The client automatically finds the leader and follows redirect hints, so it doesn't matter which node a command is sent to. Verified manually: a 3-node cluster on 127.0.0.1:910{1,2,3} elects a leader, replicates put/delete, and all nodes converge on the same commit index.

Honest Limitations

  • No log compaction / snapshotting — the log grows forever; this project intentionally keeps the log-only model to stay focused on the consensus algorithm itself.
  • No dynamic membership changes — cluster topology is a static, fixed set of nodes decided at startup.
  • One TCP connection per message — simple and correct, but not tuned for very high message rates.
  • No TLS / authentication — fine for local/demo use, not for an untrusted network.
  • Reads aren't linearized — a get is served from whichever node answers without a read-index/lease check, so it can return slightly stale data from a partitioned-away former leader or lagging follower. Writes are always linearizable through the log.
