Ark — Deduplicating, Snapshot-Based Backup Engine

A backup & restore engine built the way real tools (restic, borg) work — implemented from scratch in pure Python. Identical and near-identical data is stored only once across every file and every backup, so snapshots are cheap and incremental backups happen automatically.

Python (stdlib) Content-Defined Chunking BLAKE2b AES-256-GCM (optional) CLI Unit Tested

Overview

Ark is a content-addressed backup engine. Rather than copying whole files, it splits data into variable-length chunks, deduplicates identical chunks across every file and every snapshot ever taken, and organizes backups as immutable, git-style manifests. The core engine has zero external dependencies; encryption is an optional add-on backed by the well-vetted cryptography package.

Content-Defined Chunking

A FastCDC gear-rolling hash decides chunk boundaries based on the content of the data itself, not fixed offsets. That means inserting a single byte near the start of a large file only shifts one or two chunk boundaries instead of every boundary after it — the classic failure mode of naive fixed-size blocking. Files are chunked in bounded memory, so multi-gigabyte files back up without ever being loaded fully into RAM.

Deduplication & Snapshots

Every chunk is addressed by its BLAKE2b hash. Re-backing-up unchanged data stores zero new bytes — the repository simply references the existing chunk. Each backup run produces an immutable snapshot: a content-addressed manifest listing which chunks make up which files, so history is tamper-evident and every snapshot can be restored independently.

Capability How
Integrity verificationChunks are re-hashed on read, so bit-rot/corruption is detected, never silently restored.
Garbage collectionprune runs a mark-and-sweep over all snapshots and deletes unreferenced chunks.
Encryption (optional)AES-256-GCM per chunk, key derived from a passphrase via memory-hard scrypt.

Architecture

file ──► FastCDC chunker ──► [chunk, chunk, chunk, ...]
                               │ BLAKE2b hash each
                               ▼
                       content-addressable store
                    (compress → optionally encrypt → write once)
                               │
        snapshot manifest = { path → ordered chunk ids }  (content-addressed)
  • Backup walks the source, streams each file through the chunker, and stores every chunk via put() — a no-op if the chunk already exists anywhere in the repository.
  • Restore reads the manifest and concatenates each file's chunks back together, re-applying permissions and modification times.
  • Prune computes the set of chunks reachable from the surviving snapshots (mark-and-sweep) and deletes the rest.

Command-Line Workflow

# 1. Create a repository
python -m ark --repo /backups/photos init

# 2. Back up a directory (repeatable; later runs only store what changed)
python -m ark --repo /backups/photos backup ~/Photos --tag nightly

# 3. List snapshots
python -m ark --repo /backups/photos snapshots

# 4. Restore a snapshot (id or unique prefix) to a new location
python -m ark --repo /backups/photos restore 8954af0a /tmp/restored

# 5. Check integrity, then garbage-collect old data
python -m ark --repo /backups/photos verify
python -m ark --repo /backups/photos prune --forget <old-snapshot-id>

Testing & Design

Covered by a dedicated unittest suite spanning chunking, repository/store behavior, and snapshot integrity. The design deliberately mirrors production backup tools (restic/borg) to demonstrate real-world systems engineering: streaming I/O, content addressing, and crash-safe repository state.

Honest Limitations

  • Intra-file streaming chunker; cross-file similarity is captured only at the chunk level (no delta-compression of similar-but-not-identical chunks).
  • Snapshots are stored as a single JSON manifest — no tree-level sub-snapshot sharing yet, though chunk-level dedup already makes incrementals cheap.
  • Local filesystem backend only (no remote/object-store backends yet).
  • A backup is only as safe as the medium it lives on — an off-site copy is still recommended.
