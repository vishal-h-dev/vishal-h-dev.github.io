Sentinel — Static Security Scanner for Python/Django & AI Apps

A self-contained static analysis engine that points at a codebase and reports likely vulnerabilities: hardcoded secrets, injection sinks, insecure Django settings, missing authorization, and — the novel part — AI/LLM-specific risks like prompt injection and agent SSRF. Everything runs locally with only the Python standard library: no network calls, no API keys, no external services.

Overview

Modern applications — especially those assembled quickly with AI coding assistance — tend to accumulate the same classes of security bugs over and over. Sentinel reads source code, understands its structure (not just text), and flags dangerous patterns with an explanation and a suggested fix. It works like professional tools such as bandit, semgrep, and snyk, at a scale small enough to read and understand end to end.

How It Works

  1. Walk the project, reading every text/Python file.
  2. Parse each Python file into an Abstract Syntax Tree (AST) — a structured map of the code.
  3. Visit the tree once, matching dangerous structural patterns (e.g. an f-string built from request input passed to a raw SQL cursor → SQL injection).
  4. Scan raw text for known secret formats (cloud/API keys, private keys, JWTs) and high-entropy strings.
  5. Report findings sorted by severity, each with a CWE id and remediation guidance.

Interprocedural Taint Engine

Beyond single-function pattern matching, Sentinel includes a summary-based taint analysis that tracks untrusted data as it flows across function and file boundaries via a fixpoint over the call graph — so it can catch, for example, user input that passes through two helper functions in different modules before reaching a dangerous sink. Each finding carries the full data-flow path (file/line/description at every hop) instead of just the final line.

The Research Angle

General-purpose SAST tools are mature, but AI-agent code introduces new vulnerability classes that existing scanners largely ignore (mapped by the OWASP Top 10 for LLM Applications). The AI00x rules are a first cut at detecting them statically, built around a concrete taint-analysis model for LLM data flow:

  • Treat request.* as a source, the LLM call as a propagator (user text → prompt → model output), and eval/exec/subprocess/SQL as sinks.
  • Detect dangerous source → LLM → sink chains automatically via the interprocedural taint engine.
  • Benchmark against a labelled set of vulnerable vs. safe AI-agent snippets, reporting precision/recall vs. bandit/semgrep (which lack AI-specific rules).

Reporting & Baseline Mode

Findings can be exported as JSON (for CI pipelines/dashboards) or a detailed PDF report (rendered with the standard library only). A baseline mode fingerprints existing findings (line-insensitive, so formatting changes don't create noise) so a project can adopt the scanner incrementally and only fail CI on new issues.

Honest Limitations

  • This is a static scanner — it reasons about code without running it, so it produces some false positives and cannot catch every bug. Findings are leads to review, not proof.
  • Single-statement taint heuristics are backed by a real interprocedural engine for the sink rules it owns, but not every rule uses full data-flow analysis.
  • "No findings" never means "secure" — it means none of the implemented patterns matched.
