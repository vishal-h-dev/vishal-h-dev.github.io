BTreeDB — Disk-Based B+-Tree Key/Value Database

A dependency-free key/value database implemented from scratch in pure Python — no sqlite3, no pickle, no external storage engine. It implements B+-tree node splitting/merging directly against a paged binary file format, with a write-ahead log for crash-safe transactions and an LRU buffer pool over the page file.

Python (stdlib) B+-Tree Write-Ahead Log Buffer Pool (LRU) SQL Subset Tkinter GUI 47 Unit Tests

Overview

BTreeDB was built to demonstrate low-level database internals end-to-end: page layout, binary serialization, buffer management, write-ahead logging, and disk-based tree algorithms — the same building blocks used inside real embedded databases like SQLite and LMDB.

Storage Engine

A single file holds fixed-size pages; data survives process restarts. Only leaf nodes hold values — internal nodes hold pure routing separator keys — and leaves are linked into a sorted list, so range scans walk the chain in O(log n + k) instead of recursing through subtrees. Deleted/merged pages are returned to a free list and recycled by future allocations instead of leaking disk space.

On-Disk Page Layout

Each page is a fixed size (default 8 KiB). Page 0 is a header page (written directly, fsynced immediately, never cached/WAL'd); every other page holds one BTreeNode. Leaf and internal nodes share the exact same physical layout/capacity for simplicity — a leaf's unused "children" region is repurposed to hold its next_leaf pointer, and an internal node's "values" region is simply left unused. 

[ leaf flag: 1B ][ num_keys: 2B ]
[ key slots:   num_keys x (len: 2B + data: max_key_size) ]
[ if leaf:   value slots: num_keys x (len: 2B + data: max_value_size) ]
[ if leaf:   next_leaf page pointer: 4B (repurposes the unused child-ptr region) ]
[ if internal: child ptrs: (num_keys + 1) x page number (4B) ]

Write-Ahead Log & Transactions

Every transaction's dirty pages are logged and fsynced before being applied to the main file (redo-only, "no steal"); a crash between the WAL fsync and the checkpoint is repaired on the next open by replaying committed transactions. Every top-level insert/delete is automatically wrapped in its own durable, atomic transaction (autocommit), or grouped explicitly via BEGIN/COMMIT/ROLLBACK.

Feature Details
Buffer poolLRU page cache; never writes a page dirtied by an uncommitted transaction ahead of its WAL record.
Secondary indexesA second on-disk B+-tree keyed by value, kept in sync automatically — O(log n + k) lookups instead of a full scan.
Range queriesBacked by the leaf linked list, no subtree recursion needed for bounded ranges.

SQL Subset, CLI & GUI

A minimal SQL subset (SELECT/INSERT/UPDATE/DELETE/ CREATE INDEX/BEGIN/COMMIT/ROLLBACK) maps directly onto the KV engine, usable from the CLI or a Tkinter desktop "Workbench" GUI — an object browser with live tree stats, a query editor, and an editable results grid, styled after tools like pgAdmin/DBeaver. Zero extra dependencies; Tkinter ships with Python. 

python -m btreedb mydb.db insert user:1 '{"name": "Ada"}'
python -m btreedb mydb.db get user:1
python -m btreedb mydb.db range user: user:z
python -m btreedb mydb.db stats
python -m btreedb mydb.db sql "SELECT * FROM t WHERE key='user:1'"
python -m btreedb mydb.db gui

Testing & Benchmarks

47 unit tests cover crash recovery (a dedicated WAL crash-recovery suite), transactions, indexes, and persistence across reopen. A benchmark script compares insert/lookup/scan throughput against sqlite3 and a plain Python dict to put the engine's performance in context.

Design Tradeoffs & Future Work

  • Fixed key/value byte lengths per database file trade flexibility for a simpler, predictable on-disk layout.
  • The header page is written directly (not WAL'd) since it changes rarely and predictably — a deliberate simplification documented alongside the WAL design.
  • The SQL subset is a regex-based mapper onto the KV engine, not a full relational query planner — by design, to keep the storage engine the focus.
  • No built-in replication/clustering — this project is a single-node embedded engine (see RaftKV for the distributed-systems counterpart).
